# 生成和整理测试用例

让首次接手的测试人员可以准备数据、照步骤执行，并根据可观察的结果判断通过。

## 处理来源

- 从需求生成时，按来源明确的业务规则设计主流程、异常和边界用例。操作路径、数据或通过标准在资料中有歧义时，标为待确认，保留原文依据。
- 整理已有用例时，按原表实际列名映射字段。保留原编号、业务条件、参数、步骤和判断标准。能明确对应时再拆分或配对步骤与预期。业务含义缺失、同一编号冲突或映射有歧义时，指出影响的用例及待确认项。

## 写出可执行的用例

- 标题写明验证对象和场景。新用例使用稳定编号。
- 前置条件写本条用例开始执行时必须满足的状态、角色、权限和数据。项目通用的环境、数据准备表、术语和验收口径集中放在项目说明，用例按需引用。
- 按执行顺序写操作，交代入口、对象和需要选择或填写的值。每步配对应的预期，用可观察的提示、状态、数值或记录变化说明通过标准。
- 复核两类问题。先看未参加需求评审的人能否独立执行，再对照原资料核对关键条件、数值、顺序及预期。把仅写「正常」「正确」的结果补成来源能支持的具体断言。

## 准备 TestHub 测试包

测试包按 `project → folders → modules → cases` 组织。新建项目填写项目 `name`，已有项目可用 `id` 定位。目录和模块使用 `name`。每条用例有 `id`、`title` 和非空的 `steps`，专用前置填 `precondition`。每个步骤是一对 `action` 和 `expected`。正文省略列表序号和项目符号，保留业务编号与数值。共用说明以 `{ title, content }` 写入 `documents`。

编号使用平台接受的格式 `[A-Za-z0-9][A-Za-z0-9._-]{1,79}`，在项目内唯一。外部编号与平台格式冲突时，在交付清单保留原编号并说明需要确认的映射。平台无专用字段的来源信息保留在交付清单，或在有项目级价值时写入项目说明。执行状态和备注由平台管理。

## 交付、预检和导入

- 默认交付可执行的用例清单。目标项目及导入方式明确且配套 MCP 可用时，按工具的当前参数格式生成测试包，调用 `validate_test_package` 做只读预检。独立使用此技能时，按用户要求交付清单或测试包。
- 用户明确要求「生成并导入」「规范化并导入」或明确授权导入时，核对目标和导入模式，再预检并修正结构错误。目标或业务规则仍有歧义时，先确认受影响的用例。
- `create` 用于新建项目，`append` 用于追加新编号，`upsert` 用于按编号新增或更新并保留平台执行状态和备注。更新现有项目时先用 `list_test_projects` 和 `get_test_project` 核对目标、原编号和目录。用户只要求更新时，确认每个提交编号都已存在。计划更新项目说明时，将已有说明和本次补充一起提交，因为 `upsert` 提交的 `documents` 会替换项目说明。
- 预检通过后，用 `import_test_package` 执行已明确要求的导入。用 `get_import_result` 核对批次和新增/更新数量，必要时回读原编号、用例和执行状态。
